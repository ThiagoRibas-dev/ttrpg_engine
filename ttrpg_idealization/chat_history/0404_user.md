# Turn 404 — User

Remaining inefficiencies

1. Each DFS node recomputes prob_vector from scratch. prob_vector reruns the entire thinning chain from the first threshold every time, even though a child node's vector is just the parent's vector plus one more threshold. Since the DP state (state dict after processing the first L-1 thresholds) is exactly what the parent already computed, you're redoing O(L-1) thinning steps per node unnecessarily. The fix: thread the state dictionary itself down through the recursion (have dfs carry (state, previous_threshold) forward), so extending a vector by one threshold costs one incremental step, not a full replay. lru_cache only helps when the exact same full tuple recurs (e.g., across the three band searches) — it doesn't help sibling/child vectors share work within a single traversal.

2. Three redundant traversals per profile. all_matches is called separately for Easy/Medium/Hard, so the DFS tree is walked three times per profile. Since the bands are disjoint and the only thing that changes is the pruning floor, you could run a single traversal with the lowest cutoff (0.40, from Hard) and classify each surviving vector into whichever band its probability lands in. This would cut traversal overhead roughly threefold (the cached prob_vector calls would still be deduplicated either way, but the tree-walking and dict bookkeeping wouldn't be repeated).

3. Dead code. previous_lower, lower, and remaining_faces are computed but never used — harmless, but worth deleting for clarity.

4. Floating-point boundary risk. Since you're filtering with low<=p<=high on floats, vectors whose true probability sits exactly on a band edge (e.g., precisely 80.00000%) could be included or excluded depending on floating-point rounding in comb(n,k)*(p**k)*((1-p)**(n-k)). Given all probabilities here are exact rationals with denominator sides**pool, using fractions.Fraction for binom_pmf (or at least rounding to a fixed number of decimals before comparison) would make band-boundary inclusion deterministic rather than float-dependent. This matters more the closer a candidate vector's true probability sits to 80%, 60%, 40%, etc.

None of these are correctness bugs — the output should already be exact and complete. They're purely performance/cleanliness refinements. Given the pool sizes here (max 9 dice) and the aggressive pruning already in place, I'd expect this version to run in well under a second per profile even without applying fixes 1–2, so I'd only bother with the state-threading and single-traversal merge if you want the code itself to read as tight/canonical for the research artifact, not because runtime is likely to still be a problem.
