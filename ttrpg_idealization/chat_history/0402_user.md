4. Monotonicity gives you pruning almost for free

Adding another threshold to a vector can only keep or lower its success probability (it's a strictly more restrictive AND condition). This means:

If a partial vector already drops below 40%, every extension of it will also be below 40% — you can stop extending that branch entirely.
You never need to generate the full combinatorial explosion of long vectors up front. Build them depth-first (highest threshold to lowest), carrying the thinning-DP state forward, and prune the instant probability falls below your lowest band floor.

This changes the complexity from (number of candidate vectors) × (cost to test against full roll table) to (number of tree nodes actually visited before pruning) × (O(N) cheap update) — likely a difference of several orders of magnitude for the 8d10/9d12 cases, which is exactly where the old script froze.

5. Caching by "shape," not by exact vector

The thinning DP only depends on the bin-size pattern between consecutive thresholds (as a fraction of 
𝑆
S) and the count increments required — not on the absolute threshold values. So DC 8,6,4 and DC 7,5,3 on a d8 pool often reduce to the same cached computation if the gaps and pool are identical. Memoizing on (sorted gap-pattern, count-requirement pattern, N, S) lets you skip recomputation for large swaths of the search space, especially for evenly-spaced dice like d8/d10/d12.

Practical recommendation

Rewrite the generator as:

A tiny Binomial/thinning function prob_meets_vector(sides, pool, thresholds)) that runs the sequential-splitting DP directly — no roll table, no compositions.
A DFS/trie builder over threshold vectors (descending, 2–12, length 1..pool) that carries the DP state forward and prunes the branch the moment probability drops below 40% (the lowest band floor).
Optional memoization keyed by gap/count pattern for extra speed, though after pruning this is likely unnecessary for pools this small.

This keeps everything exact (no Monte Carlo needed) and should make even the 9d12 exhaustive search run in a fraction of a second rather than freezing, since the real cost driver was never the math — it was retesting the same statistical information (full sorted rolls) redundantly for every one of tens of thousands of vectors.
