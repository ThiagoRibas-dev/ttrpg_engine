# [AGENTS.md](http://AGENTS.md) — Agent Operating Guide (Process, Governance, and Repo Protocol)  


**Purpose:** Enable effective continuation of work if chat history is lost.  
**Non-goal:** This file contains no system mechanics, balance targets, or specific design decisions. Those live in canonical docs, the decision log, and the outstanding definitions index. If a sentence here starts describing what the game does rather than how to work on the project, it belongs elsewhere and should be moved.

## 1) What This Repo Is  
  
This repository develops a tabletop RPG ruleset using a mathless-at-the-table philosophy and a simulationist design posture. Documentation is deliberately separated into canonical rules, research/comparative analysis, conversion procedures, brainstorm/decision logs, and archived work.  
  
If you need to know what the rules *are*, do not use this file — follow the source-of-truth hierarchy below.  
  
---  
  
## 2) Source-of-Truth Hierarchy  
  
When sources conflict, resolve in this order:  
  
1. **Explicit user decisions made in the current working session**, even if not yet written down anywhere.  
2. **Canonical rules** — `03_core_baseline_system/`, `04_simulationist_subsystems/`.  
3. **The decision log** — `06_brainstorming_logs_and_roadmap/01_master_brainstorm_log.md`, "Core Design Decisions Log" section.  
4. **The outstanding definitions index** — `06_brainstorming_logs_and_roadmap/03_outstanding_definitions_index.md`.  
5. **Research, comparative analysis, and simulations** — `02_comparative_system_analysis/`, `06_brainstorming_logs_and_roadmap/02_probability_and_dice_simulations.md`.  
6. **Conversion procedures** — `05_conversion_and_content_engine/`.  
7. **Archive** — `07_archive/`.  
  
**Rules:**  
  
- Archived or deprecated material is retained for reference only and must never override canonical rules, regardless of how detailed, polished, or recent it looks.  
- Do not infer authority from a document's age, length, or level of detail. A short recent canonical entry outranks a long, old, elaborate one.  
- If nothing in this hierarchy resolves the question, treat it as **open** and present options rather than deciding silently.

## 3) Decision Status Vocabulary  
  
Every significant design question carries one of three statuses. This file does not track individual statuses — the outstanding definitions index does — but every agent must use this vocabulary consistently:  
  
- **Locked** — settled architecture. Do not revisit without a strong reason and explicit user approval.  
- **Provisional** — direction accepted; implementation or balance details still open.  
- **Open** — undecided; must be discussed and resolved before implementation.  
  
Consult `06_brainstorming_logs_and_roadmap/03_outstanding_definitions_index.md` for the current status of any given question. Do not infer status from how confidently or informally a document is phrased.

5) First-30-Minutes Reading Procedure

For any new agent, or after any loss of context:

Read README.md for current structure and navigation.
Read 06_brainstorming_logs_and_roadmap/03_outstanding_definitions_index.md to learn what is unresolved.
Skim 06_brainstorming_logs_and_roadmap/01_master_brainstorm_log.md for recent decisions relevant to your task.
Read the specific canonical file(s) governing the subsystem you will touch.
Only then consult research, comparative, or conversion documents as needed.

Do not begin implementation work — writing new subsystems, rewriting architecture — before completing step 4.

6) Agent Behavior Expectations

Be conservative with authority.
Do not decide major architecture by implication. If a change touches a foundational assumption, present alternatives and get explicit approval before treating anything as settled.

Prefer small, traceable changes.
Make the minimal edit that achieves the intended result. Avoid broad rewrites unless the task explicitly calls for one. When replacing content, move the old version to 07_archive/ rather than deleting it.

Don't duplicate canon.
Never copy rules, mechanics, or terminology definitions into meta-documents — including this one. Link to the canonical file instead.

7) Design-Change Protocol

Before proposing or applying a change with any real weight:

Locate the canonical home for the rule or subsystem in question.
Search the repo for related terms and prior discussion.
Check the outstanding definitions index for related open items.
Classify the change:
Editorial/clarification — no protocol needed beyond a normal edit.
Mechanical tweak within an existing framework — proceed, but note it in the decision log.
Architectural change — high risk; requires explicit user approval.
For architectural changes:
Present at least two viable options, not a single default.
Explain trade-offs: complexity, internal consistency, conversion impact, drift risk.
Do not silently overturn a Locked decision — flag the conflict and let the user decide.
Get explicit approval before treating any direction as locked.
8) Decision-Recording Protocol

A decision is not real until it is recorded. When a change is approved:

Update the relevant canonical rules document — this is the actual source of truth.
Add or update an entry in the decision log 06_brainstorming_logs_and_roadmap/01_master_brainstorm_log.md, Core Design Decisions Log section), with a new DEC-### identifier.
Update the outstanding definitions index — mark the item resolved, or split it into remaining sub-questions.
Update any research, comparative, or conversion document that referenced the prior open/unresolved state.
Update README.md only if top-level structure or navigation changes.
Move superseded documents to 07_archive/ rather than leaving contradictions sitting in active directories. Include a short note on why it was archived and what replaced it.

Rule: If a decision changes player-facing behavior, it must exist in canonical rules and be traceable via a decision-log entry. Neither alone is sufficient.

9) Terminology Governance
Canonical terminology lives in canonical documents, not here and not in a second shadow glossary.
Before introducing a new term, check whether one already exists for the concept.
If a new term is genuinely needed, define it once, in the correct canonical location, and note it in the decision log.
When encountering outdated terminology in an existing document:
If the document is canonical, update the term.
If the document is research, comparative, or archived, label the terminology as historical rather than editing it away — those documents are allowed to preserve old thinking.
Do not resolve a terminology inconsistency across multiple documents on your own initiative — flag it, unless explicitly asked to fix it.
10) Research and Simulation Standards

When a claim depends on probability, pacing, or balance:

Prefer a small simulation, enumerated table, or explicit calculation over informal reasoning.
Record assumptions, method, results, and interpretation limits alongside the artifact.
Store simulation scripts and outputs in 02_comparative_system_analysis/ or 06_brainstorming_logs_and_roadmap/02_probability_and_dice_simulations.md, not inside canonical rule files.
Treat results as evidence supporting a decision, not as the decision itself — a proposal built on simulation still requires explicit approval.
Never promote an untested probability claim to canonical status.
11) Documentation Style Rules

Canonical documents should be:

Declarative ("is / does"), not speculative or comparative.
Single-source-of-truth — no duplicate copies of the same rule elsewhere.
Explicit about procedures and edge cases.
Linked outward to research for rationale, rather than embedding long justifications inline.

Non-canonical documents should be:

Clearly labeled by kind (research, comparative, brainstorm, historical).
Allowed to contradict canon, since they are not rules.
Explicit about their own status (draft, superseded, historical) where relevant.

Archive policy:

Archive superseded documents rather than leaving them adjacent to canon.
Include a short note explaining why it was archived and what replaced it.
12) Reading-Order and Roadmap Pointers

Build a task-specific reading list using the procedure in Section 5 rather than relying on a fixed list — canonical documents and priorities will change over time, and a hardcoded reading order here would go stale.

This file is not the roadmap and should not be edited to reflect shifting priorities.

13) Completion Checklist

Before marking any non-trivial task done:

 Canonical rules updated, if rules changed.
 Decision-log entry created or updated, if the change was non-trivial.
 Outstanding definitions index updated.
 Cross-references updated (README, related docs) only where actually necessary.
 Superseded content archived or clearly labeled historical.
 No new contradictions introduced across canonical files.
14) Common Failure Modes to Avoid
Treating brainstorm notes or research as if they were canon.
Copying rules or terminology into meta-files, including this one.
Making an architectural change without a corresponding decision-log entry.
Leaving multiple contradictory "canonical" descriptions of the same thing in different places.
Quietly reviving an archived mechanic without re-approval.
Introducing terminology drift — the same concept under two different names.
Inferring a document's authority from its age, length, or apparent thoroughness rather than from Section 2.
Skipping the alternatives-and-trade-offs step for a change that turns out to be architectural.
